# A per-user watchlist served by the stocks API, and a read-only view of the default list (v3)

## Authority and status

Supersedes `docs/superpowers/specs/2026-11-13-feat-insight-001-user-watchlist-v2.md` after the
owner's correction of 2026-11-13: "Solyra doesn't use Supabase, only GCP. Stocks either." The v2
design kept the per-user list in a Supabase project behind two edge functions; that project was
never readable from the sessions that would have deployed it (v2, Decisions item 2) and the owner
has ruled Supabase out. The list now lives in stocks Cloud SQL behind three stocks API routes, the
stocks spec `docs/superpowers/specs/2026-11-14-feat-insight-001-user-watchlist-api.md`
(TeneikaAskew/stocks), and this spec is the solyra half: hooks, the Watchlist tab, the combobox and
the contract sync. The UI decisions of v2 are kept word for word where they do not depend on
Supabase. The owner approves this replacement by merging it. Version 2 keeps `status: approved` in
its file: the gate's supersedes-chain rule (`check_supersedes`, round eight) refuses the status flip
of a spec that itself superseded an earlier one, since v2 names v1, which is already superseded.
The gate still treats v2 as superseded through this spec's `supersedes` pointer (its plan check
refuses a plan that points at a spec a newer approved spec names), so no plan can be bound to v2
again; the gate rule is filed as stocks#1889, and v2's status flips once it is fixed. No code before this merge.

The stocks lock specs stand: stage A adds `GET /api/insights/watchlist/default` and pins the
ranker to the default owner; stage B turns the two old web write routes into 410 once this change
has removed every call to them (its precondition names the solyra spec v2; this v3 is the change it
means).

## Problem

Unchanged from v2, read in the code at origin/main 13dfa44 (solyra) and b61b9124 (stocks):

1. **The web watchlist is written to a table the web never reads back for the user.**
   `useAddToWatchlist` and `useRemoveFromWatchlist` (`src/hooks/useTickerSearch.ts:101-147`) call
   the stocks routes that scope rows to the signed-in email in the jobs' `watchlists` table; the
   jobs read only `'default'`, and `GET /api/insights/watchlist` ranks the caller's own, empty, rows.
   A signed-in user's Watchlist tab is empty (stocks #1215) and their picks never reach any job
   (stocks #1261).
2. **No remove control exists** although the hook and the route do (solyra #120).
3. **The auto-add implies ingest that does not happen.** `TickerCombobox` posts a `new` pick to the
   watchlist and shows an ingest notice (`src/components/shared/TickerCombobox.tsx:265-290`).
4. **Every `/api` call already carries the user's identity.** `src/lib/authedFetch.ts` wraps
   `window.fetch`, re-points `/api/*` at the configured origin and attaches the Firebase ID token to
   every gated path (`OPEN_PREFIXES` at `:51`), so a hook that calls `/api/me/watchlist` needs no
   client, no key and no second origin.

## Non-goals

- No write to the stocks `watchlists` table from solyra, ever, including the default list. Stage B
  makes the two old write routes answer 410; this change stops calling them.
- No data ingest by solyra. The stocks job of
  `docs/superpowers/specs/2026-11-14-feat-data-001-watched-ticker-ingest-v2.md` fetches daily bars,
  indicators and ticker info once per distinct watched ticker, nightly, reading the owner-free set
  from the stocks tables; until it has run for a ticker the UI says "data arrives after tonight's
  fetch", and after a run that produced nothing "no data for this symbol" (Rule 4).
- No change to the ranked panel's scoring, filters or contract beyond passing `extras`.
- No Supabase: no migration, no edge function, no Deno test runner, no CI step for it. The legacy
  research-workspace integration under `src/integrations/supabase` and
  `supabase/functions/insights-research` is out of scope and untouched.
- No change to the Settings page (solyra #121 is separate).

## Approaches considered

1. Chosen: hooks that call the stocks routes `GET`, `POST /api/me/watchlist` and
   `DELETE /api/me/watchlist/{ticker}` same-origin through the existing fetch wrapper, typed from
   the regenerated OpenAPI. One origin, one identity, one contract test.
2. The v2 design (Supabase tables and edge functions verifying the Firebase token against stocks
   `/api/me`). Ruled out by the owner; the project was never reachable from here.
3. Browser-only (localStorage). No account key, no second device, nothing to audit. Rejected.

## Design

### Hooks

`src/hooks/useUserWatchlist.ts`:

- `useUserWatchlist()`: `useQuery` with key `USER_WATCHLIST_KEY = ['me', 'watchlist']`,
  `enabled: isSignedIn` (from `useUser()`), fetching `/api/me/watchlist` with the ordinary relative
  `fetch` (the wrapper signs it). A non-OK response throws `Error(payload.detail ?? 'Watchlist
  service <status>')`; a 401 sets the signed-out state (the wrapper's `setOnUnauthorized` already
  signs the app out). Returns `{ query, signedOut, activeTickers }` where `activeTickers` is the
  upper-cased ticker list of `query.data?.tickers ?? []` only when data is present; there is no
  empty-list placeholder for an error (Rule 4).
- `useAddUserTicker()`: `useMutation` posting `{ticker, source}` (`source` is `'ui'` or
  `'combobox-auto-add'`); `useRemoveUserTicker()`: `useMutation` sending `DELETE
  /api/me/watchlist/{ticker}`. Both invalidate `['me', 'watchlist']` and `['watchlist']` on success
  so the ranked panel refetches with the new `extras`.
- `useDefaultWatchlist()`: `GET /api/insights/watchlist/default`, key `['watchlist', 'default']`,
  typed `WatchlistDefaultResponse`.

`useWatchlist()` (ranked) gains an `extras: string[]` option that sets the `extras` query
parameter. The normalized list (upper-cased, deduplicated, sorted, joined) is part of the query key,
`['watchlist', filterStr, limit, extrasKey]`, because today's key would keep serving the first
ranking when the membership resolves after the panel mounted. The Watchlist tab passes the user's
active tickers, and `[]` while the membership is still loading.

### Types and mocks

`src/types/watchlist.ts` derives `WatchlistDefaultResponse`, `MeWatchlistResponse`,
`MeWatchlistRow` and `MeWatchlistRemoveResponse` from `src/types/stocksOpenApi.gen.d.ts` once
`npm run contract:sync` has pulled the stocks operations. `src/mocks/insights.ts` gains
`MOCK_WATCHLIST_DEFAULT` (SPY, QQQ, IWM, all flags true, source `seed`) and `MOCK_ME_WATCHLIST`
(two rows, one with `last_daily_bar` set and one null), each `satisfies` its type;
`src/mocks/index.ts` resolves the two GET operations to them so `src/mocks/contract.test.ts`
validates them, and the test's request-body samples gain `POST /api/me/watchlist`.

### UI

The Watchlist tab (`src/components/insights/WatchlistPanel.tsx`, used by `/insights` and
`/ai-insights-lovable`) gets two sections above the ranked panel:

1. **Default list, Managed in Discord**: one chip per row with its flags (brief, insight, signals)
   as badges, the `as_of` time, and no add or remove control. The copy says the list is changed in
   Discord with `/watchlist add` and `/watchlist remove`.
2. **My watchlist**: the user's active tickers with a remove control each (solyra #120), the
   existing ticker search to add one, and states for loading, empty ("Nothing yet; add a ticker"),
   signed out ("Sign in to keep a watchlist"), and error (the API's detail, verbatim). A row with
   `last_daily_bar` null says "data arrives after tonight's fetch" while `added_at` is less than one
   trading session old (the session boundary from `src/lib/marketSession.ts`) and "no data for this
   symbol" after that; a row with a bar shows its date. Neither is the old ingest notice and neither
   pretends the data exists. The three states are each rendered under a fixed clock in the Vitest and
   the Playwright coverage, because a mock with a null `last_daily_bar` alone proves nothing about what
   the row says.

The ranked panel below keeps its filters and actions and ranks the default list plus the user's
tickers through `extras`.

`TickerCombobox`'s auto-add of a `new` pick calls `useAddUserTicker()` with `source
'combobox-auto-add'` and its notice reads "Added to your watchlist" with the honest data state; it
no longer posts to the old stocks routes.

### Contract sync

After the stocks user-watchlist API PR and lock stage A are on stocks main: `npm run contract:sync`
regenerates `tests/fixtures/stocks-openapi.json` and `src/types/stocksOpenApi.gen.d.ts` (three new
`/api/me/watchlist` operations, the default operation, and later the two 410 declarations of stage
B); `tests/helpers/fixtures/insights.ts` routes `**/api/me/watchlist*` with an in-memory list
answering GET, POST and DELETE and `**/api/insights/watchlist/default`; `src/mocks/contract.test.ts`
stays green because the app no longer requests the two old write operations and every new literal
is declared.

### Cross-repo contract

| Store | Table or route | Writers | Readers |
|---|---|---|---|
| stocks Cloud SQL | `watched_tickers`, `user_watchlists` (stocks spec 2026-11-14-feat-insight-001-user-watchlist-api) | the stocks routes, for the signed-in user only | the stocks routes; the ingest job's owner-free set |
| stocks API | `GET`, `POST /api/me/watchlist`, `DELETE /api/me/watchlist/{ticker}` | | solyra's `useUserWatchlist` hooks, same-origin with the Firebase ID token |
| stocks API | `GET /api/insights/watchlist/default` (stage A) | | `useDefaultWatchlist` |
| stocks API | `GET /api/insights/watchlist?extras=` | | `useWatchlist` (ranked) |

Identity: the Firebase ID token, attached by `authedFetch` and verified by the stocks API. Solyra
stores nothing per user itself.

### Capacity

n/a: no scheduled workload; one stocks read per Watchlist tab mount for each of the three
operations the tab uses, and one write per add or remove.

## Risks

- The stocks API is down: the user list is unavailable and says so (the detail), the explicit state
  Rule 4 asks for; nothing renders as an empty list.
- A user adds a ticker stocks has never fetched: the row says "data arrives after tonight's fetch"
  until the ingest job runs, then shows the bar date or "no data for this symbol".
- The contract test fails until `contract:sync` runs against stocks main holding the new
  operations; the plan orders the sync task after the stocks PRs merge, and the UI tasks that call
  the new routes are not committed before it.
- Playwright coverage is hermetic (`page.route`); the stocks API's own tests cover the routes.

## Decisions (owner, 2026-11-13)

1. GCP only; no Supabase in solyra.
2. Owner key: the Firebase account id with the verified email beside it, held by the stocks API.
3. A user's ticker outside the default list is fetched by the stocks ingest job once per distinct
   ticker (ingest v2 spec); the brief, insight and signal surfaces still read only the default list.
4. The two old stocks web write routes: blocked with 410 (stage B) once this change has removed
   every call to them.
