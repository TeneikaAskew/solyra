# An admin edits the default watchlist on /admin

## The owner's requirement

T, 2026-11-16, choosing among three plans for the stocks data clean-up (stocks spec `docs/superpowers/specs/2026-11-16-feat-data-001-spy-qqq-iwm-only.md`, draft PR TeneikaAskew/stocks#1977):

> "1 and in solyra the ability for an admin to adjust the default watch lists"

The default watchlist is the one list that decides which tickers stocks fetches and stores (that spec's Decision 1). Its Decision 16 asks for an editor on `/admin`: adding a ticker starts its as-traded history fetch, daily and 1-minute, at once; removing a ticker stops its fetch from the next run and deletes nothing. The API half is the stocks spec `docs/superpowers/specs/2026-11-16-feat-admin-001-default-watchlist-editor.md` (spec F); this is spec G, the panel.

## Scope

- **Code (one PR):** a Default watchlist tab on `/admin` with list, add, remove and flags, and each added ticker's history fetch shown until it finishes or fails; hooks and types for the five admin routes of spec F; the insights page's read-only section says where the list is edited; the contract sync; hermetic E2E with screenshots; a read-only cloud spec for the owner.
- **Order:** spec F's implementation is merged and deployed, and the IAM grants of its Close-out are in place, before this PR merges. This PR's contract sync reads stocks main.
- Code references are to solyra `main` 80c82c2 (2026-11-16) and stocks `main` a34bbd40. "Read" means read in the source.

## Problem

Read:

1. **The web cannot edit the default list.** `DefaultWatchlistSection.tsx` shows it read-only under the heading "Managed in Discord" (`:20`) with the note "Changed in Discord with /watchlist add and /watchlist remove" (`:51`), and has no control. `useDefaultWatchlist` reads `GET /api/insights/watchlist/default` under the key `['watchlist', 'default']` with a 5-minute stale time and the comment "Changes only when Discord or the CLI edits it." (`src/hooks/useUserWatchlist.ts:212-220`). The text is asserted by `WatchlistPanel.sections.test.tsx:90-95` and `tests/insights/watchlist.spec.ts:155`.
2. **`/admin` has three tabs.** `ADMIN_TABS` holds `users`, `data` and `models` (`src/routes/AdminPage.tsx:18-22`), kept in local state (`:38`) and rendered only when `useUser` reports `isAdmin` (`:53`); a non-admin gets the "Admin access required" card. `tests/admin/admin-tabs.spec.ts:26-45` walks the three.
3. **How admin panels fetch.** Every `/api` call is a relative `fetch` that `src/lib/authedFetch.ts` signs with the Firebase ID token (solyra CLAUDE.md, Auth). `useAdmin.ts`'s `adminJson` (`:262-274`) throws `unauthorized` for a 401 or 403 and otherwise `<METHOD> <url> failed: <status> <body>` with the raw body, which shows raw JSON on a refusal (solyra#148). `readWatchlistResponse` (`src/hooks/useUserWatchlist.ts:67-74`) reads the API's `detail` into a `WatchlistServiceError` with its status (`:32`); neither is exported.
4. **Types and mocks.** Newer response types are derived from the generated OpenAPI types (`src/types/watchlist.ts:44-60`); `src/mocks/admin.ts` holds the admin payloads (`adminRoutes`, `:297`) shared with the E2E fixtures (`tests/helpers/fixtures/admin.ts`, `mockAdminApi`, routes at `:86-142`); `src/mocks/contract.test.ts` validates every requested `/api` literal, its verb, mock payloads, request-body samples and query names against the vendored OpenAPI document (solyra CLAUDE.md, Rule 6).
5. **A missing value.** `NA` in `src/lib/format.ts:12` is the placeholder for a missing value; `isoToEtZoned` (`src/lib/time.ts:52`) formats an instant in Eastern time. A date-only string parsed through `Date` reads as UTC midnight, a day early west of UTC (solyra#114).
6. **Cloud specs exist now.** `tests/catalysts/earnings-history.cloud.spec.ts`, `tests/signals/score-explanation.cloud.spec.ts` and `tests/playbook/orb-parity.cloud.spec.ts` run under the `cloud` project with `npm run e2e:cloud` (`playwright.config.ts:151-165`).

What spec F gives the panel (stocks spec, Design 4): `POST /api/admin/watchlist/default` (201 with the row, the symbol check, the plan and the two history starts; 409 active or full; 422 shape or unlisted; 503), `PATCH` and `DELETE /api/admin/watchlist/default/{ticker}` (DELETE refuses the last active ticker with 409 and reports the cancelled executions), `GET /api/admin/watchlist/default/{ticker}/history` (each job's state, the stored daily and 1-minute ranges, the combined state `fetching`, `done`, `done_without_minute_bars` or `failed`, and `builders_not_covering`) and `POST .../history` (retry; 429 inside a 60 s lease). Every route answers 401 without sign-in and 403 without the admin role.

## Non-goals

- No change to the per-user list, `useUserWatchlist`, `useAddUserTicker` or the combobox.
- No new list route: the panel reads the list from the existing `GET /api/insights/watchlist/default`.
- No delete of stored data from the panel, and no control on the insights page.
- No URL routing for the admin tabs.

## Approaches considered

1. **A fourth `/admin` tab with its own panel, hooks in `useAdmin.ts`, types from the generated OpenAPI types (chosen).** Every admin surface is a tab with a panel file (`UsersPanel.tsx`, `DataSourcesPanel.tsx`), and the role check already wraps the tabs.
2. **Controls on the insights page's section for admins.** It mixes an operator tool into a user page and puts write controls one role check away from every user. Not taken.
3. **A section in the Chart & report data tab.** That tab is a freshness table of datasets; the list is configuration. Offered as Decision 1's alternative.

## Design

### 1. Types and the contract

- After spec F's PR is on stocks main: `npm run contract:sync` regenerates `tests/fixtures/stocks-openapi.json` and `src/types/stocksOpenApi.gen.d.ts` (never by hand).
- `src/types/watchlist.ts` derives from `components['schemas']`: the add request and response, the flags request, the row, remove, history and history-start responses. A `paths[...]` literal is avoided where it would read to the contract scanner as a request the app makes, as that file already notes (`:59-60`).
- `src/mocks/admin.ts` gains a payload for each answer, typed with `satisfies`; `src/mocks/index.ts` resolves the history GET for mock-data mode. `src/mocks/contract.test.ts` then validates them, and request-body samples for the POST and the PATCH.

### 2. Hooks (`src/hooks/useAdmin.ts`)

- `useAddDefaultTicker`, `useSetDefaultTickerFlags`, `useRemoveDefaultTicker`, `useDefaultTickerHistory(ticker, enabled)` and `useRetryDefaultTickerHistory`.
- They read answers with `readWatchlistResponse` and throw `WatchlistServiceError`, exported from `useUserWatchlist.ts` for this, so the panel shows the API's `detail` and can tell a 409 from a 503 by status. `adminJson` and its callers are not changed.
- `useDefaultTickerHistory` uses the key `['admin', 'watchlist-history', ticker]`, `refetchInterval` 15 s while the answer's state is `fetching` and `false` otherwise (Decision 3), and no placeholder data: until the first answer the panel shows loading, never "not started".
- Each mutation invalidates `['watchlist', 'default']` (the list on both pages) and the ticker's history key.

### 3. The panel (`src/components/admin/DefaultWatchlistPanel.tsx`)

- **List.** One row per active ticker in the order the API returns (added time, then ticker): the ticker, its source and added time, and three labeled checkboxes, brief, insight and signals. A toggle sends `PATCH` with that one flag and is disabled while its request is in flight; a failure shows the detail on the row and the checkbox shows the stored value from the refetched list, not the clicked one.
- **Add.** A ticker input (upper-cased as typed), the three flags unchecked (Decision 5) and Add. On 201 the row appears, the answer's symbol check shows (the vendor's price and latest trading day) and that ticker's History opens by itself. A refusal shows the API's detail beside the form: 422 not listed or bad shape, 409 already on the list or the list is full (the detail names the job that caps it at 25), 503 the vendor or database unavailable. A history start that failed inside a 201 shows "History fetch not started" with the reason and Retry.
- **Remove.** A Remove button per row opens an in-page confirmation (Decision 4): "Remove <T> from the default watchlist? Its stored data is kept. Fetching stops from the next run, and a running history fetch is cancelled." Cancel closes it; Confirm sends `DELETE`. The answer's cancelled executions and any cancel failure show on the row's place until the list refetches. A 409 for the last ticker shows its detail.
- **History, per row (Decision 2).** A History disclosure loads `GET .../history` when opened. It shows each job (daily, 1-minute) with its state and execution name; the stored daily range and 1-minute range against the planned range ("stored through 2019-06 of 2015-01 to 2026-11"); the combined state; and the builders that do not cover the ticker, from `builders_not_covering`, under "Not built for this ticker". Retry shows when the state is `failed` and sends `POST .../history`; a 429 shows its detail. A history read that fails shows its error line and keeps no finished state.
- **States.** Loading (spinner), empty (no active row: "The default watchlist is empty", a state the API refuses to create but can still read), error (the detail), permission (the page's denied card; a 401 or 403 from a route shows its detail on the panel, as the other tabs do).
- Pure display rules live in `src/components/admin/defaultWatchlistFormat.ts` and are tested there: missing values render as `NA`, 1-minute instants in Eastern time through `isoToEtZoned`, daily dates as the strings the API sends.
- Accessibility: every control is a native button, checkbox or input with a label; the confirmation moves focus to its Confirm button and returns it to the row's Remove on close.

### 4. `AdminPage`

`ADMIN_TABS` gains `{ id: 'watchlist', label: 'Default watchlist' }` after `data`, rendering a section with a heading and one line: "The tickers stocks fetches and stores each night. Adding one starts its daily and 1-minute history now; removing one stops its fetch and keeps its data." and the panel.

### 5. The insights page

`DefaultWatchlistSection` keeps its read-only list and flags. Its heading becomes "Default watchlist" and its note "Edited by an admin on the Admin page (Default watchlist tab) or in Discord with /watchlist add and /watchlist remove" (Decision 6). The comment above `useDefaultWatchlist` names the Admin page as a writer; its stale time stays.

### 6. Tests

- Unit: `src/hooks/useAdmin.watchlist.test.ts`, `src/components/admin/defaultWatchlistFormat.test.ts`, and the updated `WatchlistPanel.sections.test.tsx`.
- Hermetic E2E: `tests/admin/admin-watchlist.spec.ts` (new), with `mockAdminApi` answering the five routes and the default list, and the updated `tests/admin/admin-tabs.spec.ts` and `tests/insights/watchlist.spec.ts`. Screenshots are taken by the test (`page.screenshot` into `testInfo.outputPath(...)`), since `npm run e2e` runs with Playwright's screenshot option off (AGENTS.md, Browser proof).
- Cloud: `tests/admin/default-watchlist.cloud.spec.ts`, read-only by construction (a route handler aborts and fails on any write), run by the owner after both deploys (Close-out). The live add is the owner's own step, since it writes production rows and starts real fetches.

## Capacity

n/a for a workload: solyra runs no job. Requests, for the record: opening the tab is one list read (cached 5 minutes, shared with the insights page); an add is one POST then one list refetch and one history read; an open History while fetching is one read every 15 s, so about 100 reads over a 24-minute history and about 280 over the 69-minute high estimate of spec F's Capacity; a toggle or remove is one request and one refetch.

## Decisions for the owner

Each is written into the text as recommended.

1. **A fourth tab, Default watchlist, on `/admin`.** Alternative: a section inside the Chart & report data tab.
2. **History loads per row on demand**, and opens by itself for a ticker added in the session. Alternative: load every row's history on opening the tab, one request per row (up to 25).
3. **Poll every 15 s while a history is fetching**, and stop at done or failed. Alternative: 60 s, a quarter of the requests, slower to show the end.
4. **An in-page confirmation for Remove** that says stored data is kept and a running fetch is cancelled. Alternative: the browser's `confirm()`, which cannot carry that text reliably or be tested the same way.
5. **The add form's flags start unchecked**, as the table's defaults and Discord do. Alternative: brief and insight checked, which spends AI insight budget for every add.
6. **The insights section names both writers for every viewer, with no link.** Alternative: an Edit link to `/admin` for admins, which needs the tab to be chosen from the URL.

## Risks

- **The panel ships before the API.** Every route would answer 404 and the tab would show only errors; the order (spec F merged and deployed first) and the contract sync, which cannot pass before spec F's operations are on stocks main, prevent it.
- **A poll left running.** The 15 s poll stops at any state but `fetching`, and a history read error does not keep polling as if fetching; the hook test covers both.
- **A failed history start hidden inside a 201.** The panel shows "History fetch not started" with the reason, never a fetching state for a start that did not happen; the E2E covers it.
- **A stale list after an edit from Discord.** The 5-minute stale time is kept; the panel's own writes refresh it at once.

- Spec F's exact response field names: this spec names them from spec F's Design, and the contract sync fixes them.
- How the deployed site behaves under the cloud spec: run by the owner after both deploys.
