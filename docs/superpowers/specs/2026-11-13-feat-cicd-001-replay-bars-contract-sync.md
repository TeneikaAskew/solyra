# Contract sync for the replay-bars error responses

## Problem

The stocks spec `docs/superpowers/specs/2026-11-13-feat-replay-001-replay-bars-from-the-table.md`
(FEAT-REPLAY-001, read at stocks commit 7df792b4) declares error responses on four routes (its
Design 7) and regenerates `platform/api/openapi.json`:

- a new schema `ErrorDetail` with one field, `detail: str`;
- `responses` 404 and 503 on `GET /api/market/data/{ticker}/{date}` and
  `GET /api/market/reference/{ticker}/{date}`;
- `responses` 503 on `POST /api/backtest/replay-trades` and `POST /api/style/mine-and-validate`.

Its implementation PR does not exist yet. Its branch will be
`fix/feat-replay-001-replay-bars-from-the-table`.

Solyra Rule 6 binds the two repositories. solyra vendors that document as
`tests/fixtures/stocks-openapi.json` and generates `src/types/stocksOpenApi.gen.d.ts` from it
(`scripts/sync-api-contract.mjs:26-27`). CI runs `npm run contract:check` against stocks main on
every pull request and on every push to main (`.github/workflows/ci.yml:30-34`, `:90-91`), and the
docs audit runs the same check (`scripts/docs-audit.mjs:6099`). From the moment the stocks PR
merges, both are red on solyra main and on every solyra PR until the vendored copy follows.

What is true at solyra main 13dfa44, run on 2026-11-13:

- The vendored snapshot equals `platform/api/openapi.json` of stocks 7df792b4 as parsed JSON. The
  stocks file is the same at the stocks `origin/main` of the drafting checkout (f43447fb).
- It holds 95 paths and 98 operations. `ErrorDetail` occurs 0 times in the snapshot and 0 times in
  the generated types. Each of the four operations lists `200` and `422` only.

## Non-goals

- No change to any screen, hook, hand-written type, mock, fixture, request or test. The UI that shows
  the two states and limits the Replay calendar is a separate solyra spec that follows the stocks
  change.
- No change to `src/mocks/contract.test.ts` (Design 3) or to `scripts/sync-api-contract.mjs`.
- No hand edit of either generated file.
- The deployed-site check. It is its own spec:
  `docs/superpowers/specs/2026-11-13-feat-cicd-001-replay-bars-cloud-spec.md`.

## Approaches considered

1. Carry the sync inside the solyra UI spec's PR. Rejected: `contract:check` would stay red on main
   until that screen work is specified, built and reviewed.
2. Open the sync only once the stocks PR has merged. Rejected: main is red for as long as it takes
   to open and review a PR that could have been reviewed beforehand.
3. A standalone sync under FEAT-CICD-001, drafted from the stocks PR branch before that PR merges
   (chosen). It is the shape of the ping sync, `2026-11-09-feat-cicd-001-ping-contract-sync.md`
   (PR 323): FEAT-CICD-001 owns the contract check, and a sync that touches only the two generated
   files has no other capability's code in it. The market-hours sync (FEAT-ADMIN-001, PR 317) and
   the similar-setups sync (FEAT-CHART-001, PR 327) were filed under a product capability because
   each also changed a hand-written type, a mock or a screen. This one does not (Design 3 and 4).

A `chore/` branch cannot carry either file: its allowance is manifests, lockfiles and the gate's
own files (`scripts/gate/spec_gate.py:1585-1601`).

## Design

### 1. The command and the files

- Branch `fix/feat-cicd-001-replay-contract-sync`, opened as a draft once this spec is approved and
  on main and the stocks branch holds its regenerated `platform/api/openapi.json`.
- `STOCKS_OPENAPI_REF=fix/feat-replay-001-replay-bars-from-the-table npm run contract:sync` writes
  both files (`scripts/sync-api-contract.mjs:28-29`, `:92-98`). Nothing else writes them.
- The plan records the source pin (stocks commit, blob and SHA-256 of the fetched `openapi.json`)
  and the SHA-256 of both written files, as the ping-sync plan does. On main today the two files are
  `6fcff822e0c609670efcc9a179815d479322ae0365316b617654e6e2c0fc9d26` (snapshot) and
  `fbda45304fc95bf5a41b58da9f1ae0187c732fa933a5c6f4c5de566cc2cccaa4` (types).

### 2. The expected diff

Compared as parsed JSON, the snapshot on the PR head and on `origin/main` are equal once these are
removed from both:

- `components.schemas.ErrorDetail`;
- `responses.404` and `responses.503` of the two GET operations;
- `responses.503` of the two POST operations;
- `description` and `summary` of the four operations (a docstring the stocks PR rewrites shows
  here).

Anything else that differs fails `done_when` item 1 and stops the sync. The plan runs that
comparison as a command and the PR description carries its output.

What the six entries and the schema look like was prototyped on 2026-11-13 with a two-route FastAPI
app (FastAPI 0.143.3, pydantic 2.13.5, the versions with which `python scripts/export_openapi.py
--check` reports the stocks snapshot of 7df792b4 up to date):

- each entry is `{"content": {"application/json": {"schema": {"$ref":
  "#/components/schemas/ErrorDetail"}}}, "description": ...}`, with description `Not Found` for 404
  and `Service Unavailable` for 503;
- `ErrorDetail` is an object schema with `additionalProperties: true`, one property `detail` of
  type string, and `required: ["detail"]`.

Adding exactly those to main's snapshot gives 74 added lines and none removed. In the generated
types each entry should take 9 lines, by the shape of the existing 422 entries
(`src/types/stocksOpenApi.gen.d.ts:8003-8011`), plus the `ErrorDetail` type.

The byte-level diff is not checked: the stocks branch does not exist, and the generator cannot run
in the drafting checkout, which has no `node_modules`. `done_when` item 1 is checked on the PR head.

### 3. `src/mocks/contract.test.ts` needs no change

Decided from its code; the test was not run for this spec, for the same reason.

- It reads three things of an operation: `responses['200']` (`:612`), `requestBody` (`:822`) and
  `parameters` (`:1081`). Its `Operation` interface declares the three (`:71-75`). It never reads a
  404 or a 503 entry.
- It resolves `$ref` against `components` (`:593-598`). `ErrorDetail` is added there and no 200
  schema refers to it.
- No path, verb, parameter, request body or 200 schema changes, so its checks see the same input.
  Its printed lines should not move: `done_when` item 3 compares them with main's.
- By a Python reading of the snapshot with the test's own rule (`:611-618`), main has 81 typed and
  17 untyped operations and 95 declared paths. What vitest prints today is not checked.

### 4. No hand-written type, mock or fixture changes

- The stocks spec changes no 200 body. `MarketDataResponse`, `ReferenceResponse`,
  `ReplayTradesResponse` and the two style schemas keep their shape (its Design 7: "The other codes
  keep the shapes they have").
- `src/types/assignability.ts` pairs hand-written response types with generated 200 schemas.
  `ErrorDetail` has no hand-written pair and none is added: no solyra code is typed against it yet.
  The readers take `detail` as a string already (`src/hooks/useMarketData.ts:48-55`,
  `src/hooks/useJournalChartTrades.ts:591`, `:764`).
- The mock-mode answers for the four routes (`src/mocks/charts.ts`, `dashboard.ts`, `journal.ts`,
  `live.ts`) and the fixtures under `tests/helpers/fixtures/` are 200 bodies, with one exception:
  the `replay-trades` mock also answers that route's own 422 and its 404
  `no matching trades found` (`src/mocks/charts.ts:206-215`). The stocks spec changes neither
  text and does not add that 404 to the document. All of these stay as they are.
- `src/mocks/live.ts` names the two GET routes in its header comment (`:13-15`) and answers the
  bars route for IWM with a 200 body (`:303-304`). It leaves the reference route to
  `src/mocks/dashboard.ts` (`:306-308`). It needs no change.
- `tsc -b` and the full vitest run on the PR head are what prove this (`done_when` item 3).

### 5. Merge order, and what is red when

| When | solyra main and other solyra PRs | This PR |
|---|---|---|
| Before the stocks PR merges | `contract:check` green | `contract:check` red (its snapshot is ahead of stocks main); `tsc -b`, vitest and the build green |
| From the stocks merge until this PR merges | `contract:check` and the docs audit red | green once CI is re-run |
| Once this PR has merged | green | |

1. The cloud-spec PR of the other spec merges first. It does not depend on this one.
2. This PR is opened as a draft from the stocks branch. The stocks PR links it in its description
   and states the order.
3. The stocks PR merges. This PR's CI is re-run and `contract:check` passes against stocks main. If
   the stocks head moved before its merge, the sync is re-run from stocks main and re-pinned.
4. This PR merges with current-head review and the owner's authorization. Nothing here deploys.

Capacity: n/a, solyra runs no workload. One fetch of one file at sync time.

Plan size: four tasks, as the ping-sync plan (regenerate and pin; verify; open and record; close
once the stocks PR has merged).

## Risks

- The stocks PR changes something else in the document, for example another route's description.
  The comparison of Design 2 refuses it. The sync stops until the owner says whether that change
  belongs here.
- Another stocks change that regenerates `openapi.json` reaches stocks main first. solyra main is
  then red for that change, and its sync is that change's work. This sync is re-run once it has
  landed. Item 1 is measured against solyra `origin/main`, so it still shows only this change.
- The stocks head moves between the draft and the merge. `contract:check` against stocks main
  catches any difference (item 2) and the sync is re-run then.
- This PR and the cloud-spec PR both edit the FEAT-CICD-001 catalog row. The second to merge takes
  main in with a merge commit. It is never rebased (Rule 0).
- A reader could take the new 404 and 503 declarations as covered by the contract test. They are
  not: it validates 200 bodies only. The texts are pinned by the stocks API tests. In solyra the
  unit tests of the cloud-spec change (`src/lib/replayBarsContract.test.ts`) pin the bars 404 text
  exactly and the prefix of every row of the stocks Design 7 table. Until that change merges,
  nothing in solyra pins them.
